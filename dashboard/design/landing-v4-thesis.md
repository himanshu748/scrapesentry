# ScrapeSentry landing page v4

## Design read

Technical product landing page for hackathon judges and scraper operators. The visual language is an editorial instrument: restrained, operational and evidence-led.

- Design variance: 7. The composition is asymmetric but the data flow remains immediately legible.
- Motion intensity: 6. Motion explains ingestion, validation, quarantine and release.
- Visual density: 5. The interface carries real product evidence without becoming a dashboard above the fold.

## Existing-site audit

- Brand tokens: white canvas, graphite type and hardware, green verified state, red quarantine state, Geist and Geist Mono, mostly sharp two-pixel corners.
- Information architecture: Product, Console, Docs and Evidence routes with the failure lab as the primary landing-page action.
- Useful content: contract scanner, false-success explanation, runnable failure lab, recovery states, integration instructions and production receipt.
- Preserve: the headline, physical contract-gate render, real console captures, provider identifiers, route structure and direct technical voice.
- Retire: the right-to-left scanner flow, late Bright Data explanation and the weak relationship between provider collection, contract enforcement and Self Healing.

## Design thesis

- Product truth: Bright Data is the production data plane. ScrapeSentry is the release-control layer that stops unsafe collector output and verifies recovery.
- Audience: WeMakeDevs judges, data engineers and teams operating Scraper Studio collectors.
- Desired feeling: complete, credible and mechanically understandable.
- Primary action: run the failure lab.
- Visual concept: a left-to-right production line from Bright Data collection to contract validation to verified downstream output.
- Primary archetype: technical instrument.
- Secondary influence: data story.
- Page silhouette: asymmetric opening, provider integration spine, false-success receipt, interactive failure lab, captured recovery theatre, adoption lanes and evidence ledger.
- Type strategy: Geist for decisive product language, Geist Mono for provider identity, contracts and receipts.
- Material and color language: white technical paper, graphite machinery, one green success accent and red only for blocked data.
- Media strategy: the existing product-specific contract gate and real console captures. No decorative generated media is required.
- Signature moment: incoming Bright Data rows enter from the left, a failed row drops into quarantine and verified rows leave on the green right side.
- Cliches to avoid: a dashboard-card hero, an invented customer-logo wall and generic feature tiles.

## Content hierarchy

1. State the silent-failure problem and show the working data path.
2. Establish Bright Data as the collector and Self Healing provider.
3. Explain why HTTP 200 is insufficient.
4. Let the visitor break the data contract.
5. Show the guarded repair and release states.
6. Explain how to connect a real collector and MCP client.
7. Close with traceable production evidence.

## Console readiness refinement

- Design read: targeted evolution of an operational console for technical evaluators.
- Design variance: 5. Keep the established grid and sharpen the status hierarchy.
- Motion intensity: 3. Use native disclosure feedback instead of decorative animation.
- Visual density: 6. Present three decisive states, then reveal deployment detail on demand.
- Product truth: the recovery workflow is complete in recorded-evidence mode. Persistence, scheduling and incident routing are scale controls rather than missing product features.
- Signature moment: one horizontal status rail separates what is verified now from what is optional before customer traffic.

## Scenario matrix hardening

- Design read: targeted evolution of the existing technical instrument, not a new visual direction.
- Product truth: one contract engine blocks structural drift, quality collapse, semantic corruption and incomplete crawls.
- Primary action: select one failure cartridge, run it and inspect the scenario-specific contract receipt.
- Signature moment: four unrelated scraper failures enter through the same Bright Data evidence path and stop at the same release gate while the 12-row verified feed stays available.
- Layout model: an open failure library beside one instrument panel. Avoid a generic equal-card feature grid.
- Mobile behavior: the failure library becomes a horizontal scroll-snap rail, then the instrument recomposes into a vertical source-to-gate-to-output path.
- Motion purpose: selection motion confirms a state change, the scan beam communicates validation and flow motion makes the protected data direction legible.
- Media decision: preserve the existing contract-gate render. The new scenario is product proof, so no decorative generated asset is needed.
